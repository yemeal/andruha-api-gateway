# AGENTS.md — api-gateway

Адаптация `docs/agent-guidelines/AGENTS.md` из Andruha для NGINX. Файл самодостаточен при отдельном checkout; специфичные для Python/Pydantic правила заменены проверками gateway.

## Работа и согласования

- Отвечай по-русски: сначала результат, затем существенные детали. Перед сложной задачей дай краткий план: поведение, затрагиваемые границы, шаги и проверки.
- До правок прочитай локальные инструкции, README, релевантные CONTEXT.md/ADR и проверь Git status родителя и сервиса. Сохраняй чужие и незавершённые изменения; работай только в согласованной области.
- Прямое поручение разрешает необходимые изменения в его пределах. Рутинные обратимые решения принимай сам; уже полученное согласие повторно не запрашивай.
- Сначала согласуй изменения публичных API, схем БД и сериализованных событий, новые зависимости/инструменты, удаление существующих файлов или публичных интерфейсов, если это ещё не разрешено задачей.
- Аудит заканчивается выводами и конкретным планом; обнаруженные исправления и архитектурный рефакторинг выполняй после одобрения. Независимую разрешённую работу продолжай, пока ждёшь ответа.

## Git и доставка

- Каждая фича — отдельная ветка с понятным именем; по умолчанию `feat/<краткая-суть>`. Основная ветка изменяется через PR. Для независимых репозиториев — отдельные ветки и PR.
- Коммиты атомарны и идут в логическом порядке: одна ответственность, только относящиеся к ней файлы, без смеси фичи и посторонней уборки.
- Conventional Commits: `type(scope): description`; scope необязателен. Используй `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `build`, `ci`, `perf`; breaking change обозначай `!` или `BREAKING CHANGE:`.
- Перед коммитом проверь staged diff. Не включай чужие правки, секреты, токены, пароли или приватные ключи, включая тесты. Не переписывай чужую историю и не выполняй разрушительные Git-операции без явного разрешения.

## TDD и неприкосновенность тестов

- Для фичи/багфикса используй навыки `tdd` и `pytest-skill`, когда применим Python; их примеры не отменяют правила этого файла. Перед новым тестом согласуй проверяемое поведение и публичную границу; уже утверждённого задания/плана достаточно, если они определены в нём.
- Работай вертикальными шагами: один тест поведения → ожидаемый RED → минимальная реализация → GREEN. После GREEN проверь дизайн и сделай разрешённое локальное упрощение, затем повтори затронутые проверки. Не пиши заранее весь набор тестов под предполагаемую реализацию.
- **О каждом падении сообщай сразу:** команда, конкретный тест, ожидаемое/фактическое поведение, известная причина или явно отмеченная гипотеза.
- **Ожидаемый RED нового теста**, падающего именно из-за согласованного отсутствующего поведения: сообщи и продолжай реализацию по согласованному плану, не меняя тест.
- **Неожиданное падение** (включая иной повод RED): останови исправления затронутой области, представь диагностику и запроси одобрение. До ответа допустимы чтение/диагностика и независимая работа, но не изменение production-кода ради этого падения.
- **Любые изменения уже написанных тестов — только после одобрения:** assertions, fixtures, conftest, helpers, snapshots, перемещения/удаления, skip/xfail и настройки, меняющие набор или смысл проверок. Это относится и к тесту, только что написанному агентом. Не ослабляй проверки ради GREEN; намеренно оставленный пользователем RED сохраняй.
- Тестируй наблюдаемое поведение через публичные интерфейсы: результат, доменную ошибку и состояние после операции. Ожидания бери из требований/независимых примеров, а не из повторения алгоритма. Не привязывай тест к приватным методам и порядку внутренних вызовов.

## Архитектурная граница

- Это транспортный NGINX gateway: бизнес-правила, Rich Domain Models, ORM и application use cases принадлежат upstream-сервисам. Python/Pydantic-иерархия универсального шаблона здесь неприменима.
- Query-маршруты не должны скрыто создавать/исправлять бизнес-данные. Изменение публичного маршрута, заголовков или ошибок проверяй как изменение контракта.
- Переиспользуй общую конфигурацию проксирования. Согласовывай межсервисные изменения явно; транспортная задача не разрешает рефакторинг соседнего сервиса.

## Читаемый и простой код

- Пиши код как связный текст: понятные произносимые имена, небольшие функции с одной задачей и одним уровнем абстракции (SLAP). Сохраняй стиль проекта; не дроби код ради произвольного лимита строк.
- KISS/YAGNI: минимальный дизайн для текущего поведения, без speculative features, преждевременной универсальности и лишнего boilerplate. DRY: один источник бизнес-правила; похожий синтаксис не всегда означает одну абстракцию.
- SOLID: одна причина изменения (S); расширение через устойчивые точки вариативности (O); соблюдение контрактов подтипами (L); небольшие интерфейсы клиентов (I); зависимость от портов, а не реализаций (D). Полиморфизм, Factory/Strategy/Policy/Adapter применяй для конкретной необходимости.
- Комментарии объясняют бизнес-причину, компромисс алгоритма или внешнее ограничение. Непонятное «что» исправляй именованием и структурой; docstrings публичных контрактов сохраняй полезными.
- Boy Scout Rule действует внутри задачи и разрешённых файлов: убирай внесённые debug/неиспользуемые импорты/мёртвый и закомментированный код, не расширяя область и не нарушая согласования удаления или изменения тестов.
- Явно обрабатывай ожидаемые ошибки, сохраняй причину при переводе между слоями; неожиданные ошибки не проглатывай и не превращай в успех. Проверяй недоверенные данные на границах; не раскрывай секреты в логах/исключениях.
- Make it work → make it right → make it fast: сначала корректное поведение, затем разрешённое упрощение; оптимизация — после измерения, с сохранением контракта и проверок.

## Проверка и завершение

- Точные команды и версии бери из конфигурации сервиса и CI. Во время реализации запускай целевые проверки; перед завершением изменения кода — formatter/linter, type checker и обязательные unit/integration-проверки проекта. Для документации без изменения поведения достаточно относящихся к ней проверок.
- Готовность кода: обязательные проверки прошли, formatter/linter/type checker не выдают ошибок и warnings. Проверяй без автоправки защищённых тестов и подавления диагностики; существующие проблемы сообщай отдельно, соблюдая границы согласования.
- Интеграции запускай с реальными изолированными зависимостями и нужными миграциями/настройками. Недоступная инфраструктура, collection, skip/xfail и ожидаемый RED не считаются прохождением тестов.
- Заверши отчётом: что изменено, какие команды прошли, какие проверки упали/пропущены/не запускались и что блокирует завершение. Не заявляй зелёный CI, готовую интеграцию или закрытый PR без проверки соответствующего результата.

## Контекст: api-gateway

- Реализация: `nginx.conf`, `proxy-common.conf`, `Dockerfile`; слушает `8080`, upstream-имена разрешаются через Docker DNS. Здесь нет `pyproject.toml`, uv, pytest и Python-домена.
- Gateway владеет routing, proxy headers, WebSocket upgrade, timeouts, request ID и безопасным access log. Проверка JWT, прав, сессий и доменных правил выполняется в upstream-сервисах.
- Сохраняй замену клиентского `X-Request-Id` на gateway ID, передачу этого ID upstream и удаление дублирующего response header. Клиентский `Authorization` перезаписывается значением из cookie `access_token`; это преобразование не валидирует JWT.
- Логи не должны раскрывать credentials, cookie и query string с чувствительными данными. `proxy-common.conf` — единый источник общих proxy headers; изменения WebSocket `Upgrade`/`Connection` проверяй в соответствующем location.
- Текущий CI проверяет конфигурацию/сборку и smoke для health, замены request ID и JSON 404. Он не доказывает работу всех upstream API или реальной WebSocket-доставки; дополнительные проверки определяет затронутое поведение.

### Команды и проверки

Из корня сервиса:

```powershell
docker build --target runtime --tag andruha/api-gateway:local .
```

- Сборка использует validation stage с `nginx -t`; smoke-сценарий находится в `.github/workflows/ci.yml`. Для изменения конфигурации выполни проверку сборки и затронутых HTTP/WS-сценариев на изолированном контейнере.
- Новые проверки добавляй на публичной границе HTTP/WS по TDD. Изменения существующего smoke-теста в CI тоже требуют одобрения; правило неожиданных падений действует на shell/HTTP assertions.
- Статический анализ Python и pytest сюда не добавляй ради унификации. `scripts/codex-service.py` в родителе исключает этот репозиторий; проверки общей маршрутизации смотри в Compose и integration workflow Andruha.
